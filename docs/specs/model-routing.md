## Purpose
The routing plane joins catalog facts, operator policy, request demand, live quota, failure backoff, effective cost, and observed speed to select a reproducible provider/model route. It records every decision so later explanation can show the selected route, rejected candidates, provenance, objective, and outcome. (`crates/striatum-core/src/model_router.rs:409-538`, `crates/striatum-core/src/model_router.rs:557-631`, `crates/striatum-module/src/main.rs:1918-1920`)

## Vocabulary
Route key: the canonical provider and model identity; Fusiform and the store key facts by provider plus model and never by a bare model id. (`crates/striatum-store/tests/it/route_state_store.rs:2344-2383`)

Catalog fact: existence, token limits, capabilities, and output price synchronized from Fusiform, subject to a same-field operator override. (`crates/striatum-module/src/fusiform_catalog.rs:3-12`, `crates/striatum-core/src/route_state_store.rs:32-39`)

Score provenance: `Curated`, `Override`, `AaInferred`, or `Unscored`; unscored facts are known but not routable. (`crates/striatum-core/src/model_facts.rs:178-204`)

Demand: IQ and EQ numbers must be within 0 through 100; the demand-bar calculation clamps its input to that same scale. (`crates/striatum-core/src/routing_config.rs:48-62`, `crates/striatum-core/src/model_router.rs:655-667`)

Demand bar: `top_score * (demand / 100)^0.35`; a model's fit on each demanded axis is capped at 1.0. (`crates/striatum-core/src/routing_config.rs:13-13`, `crates/striatum-core/src/routing_config.rs:48-62`)

Adequacy: the demand-weighted Elo and EQ fit after confidence penalty. Normal routing requires 0.95; best effort may run from 0.60 to 0.95 and emits `belowFloor`. A consumer's `below_bar: "refuse"` setting disables best effort for automatic selection; explicit pins are unaffected. (`crates/striatum-core/src/route_scoring.rs`, `crates/striatum-core/src/routing_config.rs`, `crates/striatum-core/src/model_router.rs`)

Static admission: catalog, exclusion, availability, capability, context, and fast-variant gates applied before transient quota and cooldown state. (`crates/striatum-core/src/model_router.rs:409-538`)

IQ frontier: the maximum Elo and EQ that an IQ request is measured against come from every route that could be chosen automatically, whether or not it can send right now. A route whose accounts are held by the reserve or exhausted, whose credential is refused or fenced, or whose credential listing is stale keeps its place in the frontier, so a walled top model never makes a weaker model count as adequate for higher IQ; the request waits or is refused instead. Routes with no serving credential, an incompatible runner pair, a capability mismatch, or an operator or caller exclusion (including pin-only models) stay out of the frontier. (`crates/striatum-core/src/model_router.rs`, `admit_routes_with_availability`; `crates/striatum-module/src/routing_v1/select.rs`)

Operator exclusion: `model_routing.exclude` (groups `all`, `mason`, `sidekick`, `athena`, `lab`, `core`, with `-` exceptions inside a group) keeps a route out of automatic choice only: unpinned `route.select`, class-policy panel seats and extra draws, fallback, failover, and reroute. A request that names its model (`work(model=...)`, a synthesizer or lab-planner pin, an admission pin) is admitted even when the route or its provider is excluded, as long as it is otherwise servable: credentials, availability, capability, context window, and quota walls still refuse it. There is no separate explicit-only list; `model_routing.explicit_only_providers` is refused at load with `config_key_removed` and the remedy "list the provider in model_routing.exclude.all; an explicit model pin is still admitted". (`crates/striatum-module/src/work_model_pin.rs`, `crates/striatum-module/src/select_policy.rs`, `crates/striatum-module/src/config_overrides.rs`)

Dotted consumers such as `athena.gather` retain their full name in decision records and inherit their root group's exclusions, pin-only handling, variants, pins, panel class policy (how many seats are ranked by IQ, EQ or cost, and how many extra seats are drawn at random above the class floor), service tiers and below-bar policy. Consumer settings resolve from the most specific name through its ancestors. `consumers.<group>.below_bar` accepts `"best_effort"` or `"refuse"`; mason and its dotted descendants default to refusal, while every other consumer defaults to best effort. Model and provider `only_for` / `not_for` patterns are evaluated for each request: `athena` matches both `athena` and `athena.gather`, while `athena.gather` matches that name and its descendants but not plain `athena`. Dotted exclusions identify the matching rule in the rejection detail. An unrecognized root has no built-in consumer group or group exclusions; name-level rules still apply.

Variant overrides: `model_routing.variants` uses the same groups as `exclude` (`all`, `mason`, `sidekick`, `athena`, `lab`, `core`). Each group maps a route spec in the exclusion grammar (`provider`, `provider/model`, `provider/model/variant`; no `-` entries) to a reasoning variant, and within a group the most specific matching key wins. A selection runs at the first of: (1) a variant the caller names (`provider/model:variant`, an admission pin's or synthesizer pin's `variant`); (2) `variants.<consumer>`; (3) `variants.all`; (4) the curated default on the route's fact row. Panels apply it per seat, extra draws included: lab panels read `variants.lab`, every other class `variants.athena`. The authority for which variants exist is the catalog: Fusiform's `capability.reasoning_options`, whose `effort` values routing stores per model (`model_facts.reasoning_efforts_json`, migration 50). Startup (once the store opens) and every reload refuse an override whose variant a matched model does not publish, whose model publishes no effort values, or whose key matches no catalog model, naming the route, the variant and the published list; a refused reload keeps the last good config. `--check-config` runs the same check against the store at `$XDG_DATA_HOME/cortexkit/striatum/store.db` (default `~/.local/share/...`) opened read-only, or prints why it skipped. A model not yet read from the catalog since migration 50 is a warning, not a refusal. If the catalog later stops publishing a configured variant, selection does not fail: it uses the next rule and records the skip in `variantSelection.fallbacks` on the `route.select` reply and as `variant fallback:` lines in the decision explanation. `route.select` replies carry `variantSelection` (`variant`, `source` = `pin`, `consumer`, `all` or `curated`); panel policies carry `reasoningVariant`, `reasoningVariantSource` and `reasoningVariantFallbacks` on each `seatedVariants` entry. (`crates/striatum-module/src/variant_policy.rs`, `crates/striatum-module/src/config_overrides.rs`, `crates/striatum-store/src/reasoning_catalog.rs`, `crates/striatum-module/src/fusiform_catalog.rs`)

Pinned variants: a `modelPin` naming `provider/model:variant` is checked against the same published efforts, following a `score_alias` provider to the provider whose catalog rows it borrows. A variant outside a published list is refused with `invalid_model_variant`, naming the list. A model the catalog has not been read for yet (or a module whose store has not opened) admits the pin, leaves the decision to Broca, and adds a `not checked` line to the decision explanation. Core runs each Athena seat (round zero, spec campaigns and replacement seats) at `seatedVariants[slot].reasoningVariant` when routing sends it, and at the member's `promptParams.variant` otherwise. It records the result as `seatVariant {variant, source}` on the member in the consult's stored panel; the source is routing's `reasoningVariantSource`, or `prompt_params` when routing sent no per-seat variant. (`crates/striatum-module/src/work_model_pin.rs`, `crates/prefrontal-core-module/src/routing_cooldown.rs`)

Built-in LLM spending policy: API-key and gateway billing planes are pin-only unless they are quota-backed subscription planes. This base layer applies with or without an operator file. Explicit provider or model `pin_only: false` opts a route into automatic selection; a model-level value overrides its provider. Explicit `subscription: true` also exempts a flat-rate API-key plan from the built-in spend fence, but does not clear an explicit pin-only rule. A model's `subscription: false` replaces its provider's true and leaves the billing plane authoritative. Subscriptions remain automatic. Code-mode and flow one-shot calls share these defaults; only an explicit consumer `pay_per_token: true` restricts a consumer to metered accounts (`role.describe` reports that restriction as `priced_only`). Classify and extract calls choose models through the separate classifier path, which this spending policy does not fence. Media engines are exempt from this built-in LLM fence: they have no subscription alternative or pin member, and remote transcription and speech remain automatic without engine opt-ins. Explicit operator `not_for` rules and consumer exclusions still refuse a remote engine, but pin-only rules do not, because an engine has no pin operation and a pin-only rule would otherwise make it unusable; caller-local engines remain available. Runner enrollment still requires a `runners` entry in routing settings; automatic first-party enrollment awaits a daemon-attested catalog mark verifying that a module belongs to CortexKit itself, not merely that the daemon launched it. The unmeasured subscription price multiplier remains 1.0 (no subsidy relative to the stated rates), and no spend budget is installed by default.

Effective price: output list price divided by a positive finite subscription multiplier; unknown price normalizes to maximum cost rather than zero. An explicit service tier scales subscription consumption by the account plan's included-usage or credit rate; API-key traffic uses the model's mode rates instead. (`crates/striatum-core/src/model_router.rs`; `crates/striatum-module/src/service_tiers.rs`)

Selection cost: economic cost (normalized effective price plus legacy quota pressure weighted by 0.5) multiplied by an overqualification factor. With IQ surplus `s` on the request's 0–100 demand scale, the factor is `1 + min(3, 0.05 × (2^((s − 40)/10) − 1))` above surplus 40, otherwise 1. No IQ demand means no surcharge. It is monotone and bounded to 1–4: surplus 50/60/70/80/90 costs 1.05/1.15/1.35/1.75/2.55 times as much. Thus low-demand work requires a flagship to be clearly cheaper, while demand 60 and above is untouched. The operator's existing `overqualification.threshold`, `doubling` and `base` fields set the threshold, step and fractional surcharge; `base: 0` disables it. The recorded `overqualification` remains the surcharge in cost units, already included in `selectionCost`; explanations also show the multiplier. The fit guard still prevents moving to a route that fits less well. Truly zero-cost routes stay zero-cost, and economic tie bands still apply. (`crates/striatum-core/src/model_router.rs`, `apply_overqualification`; `crates/striatum-core/src/routing_config.rs`, `OverqualificationConfig`)

Effectively-free bucket: routes at or below selection cost 0.05 compare adequacy before speed and ignore smaller cost differences. (`crates/striatum-core/src/routing_config.rs:82-82`, `crates/striatum-core/src/model_router.rs:831-848`)

Quota wall: a route or account exclusion caused by explicit exhaustion, utilization at or above 0.99, or a reported spendable non-positive pool. (`crates/striatum-core/src/quota.rs:249-306`, `crates/striatum-core/src/quota.rs:114-125`)

Broca floor: a preference, not a wall. A new Broca run prefers an account with at least `broca_floor_points` (default 5) spendable on every general window, because a Broca run stays on its account and ends at the first account limit, so it cannot move mid-run the way a plugin session can (the prefrontal repository's `docs/designs/account-selection.md`, "New-session rule" step 4). When no account clears the floor, the account with the most spendable points left is admitted with reason `cold_below_broca_floor`, and its account note keeps the `below_broca_floor` entry. The reserve, fences, policy floors and walls still exclude. (`crates/striatum-core/src/accounts/eligibility.rs`, `QuotaEval::eligible_below_broca_floor`; `crates/striatum-core/src/accounts/decide.rs`, `Allocator::cold`)

Failure backoff: route-local cooldown whose default threshold is three consecutive route-attributable terminal failures; it begins at ten minutes and doubles to a one-hour cap. At its recheck, one request atomically claims the probe; an expired timestamp never opens unlimited requests. (`crates/striatum-core/src/failure_backoff.rs`, `crates/striatum-store/src/fence_rechecks.rs`)

Routing decision: the durable selected route, request, candidate explanations, policy provenance, and later outcome addressed by decision id or send id. (`crates/striatum-store/src/lib.rs:485-537`, `crates/striatum-module/src/main.rs:3166-3282`)

## Surfaces
- Head model choices: the read-only query `route.head_choices {runner_module}` lists what the Alfonso apps' model and speed picker may offer a head (an agent's main session, the one the user talks to) on that runner. It returns `{catalog_version, runner_module, models: [{provider, model, pin_only, billing, variants, default_variant?, service_tiers}]}`, sorted by provider and then model, unranked. `provider` and `model` are the ids core's `runner_head.set_model` takes.
  - **`pin_only`:** true when routing would run a head on this model only if the head pins it, and never picks it for a head by itself.
  - **`billing`:** how the account serving this model on that runner is paid for. It's `subscription` when at least one account that reaches the model through this runner counts as a subscription under routing's account rules, settings `subscription` flags included, and `pay_per_token` otherwise. Treat any other value as unknown.
  - **Which models:** a model is listed when an account reachable through that runner can serve it and the head policy a pin uses admits it (`only_for`, `not_for`, provider model lists). Routing-only providers that borrow catalog rows through `score_alias` and have no catalog rows of their own are listed only when a reachable gateway credential serves the pool through a `gateway` pair the runner explicitly declares for the model's wire family. Such runners can name gateway provider ids in their plans; non-gateway pool aliases such as `anthropic-platform` are not listed. `pin_only` models are listed, because a person picking a model is a pin. Models a pin can't reach (deprecated, unscored, unavailable, no serving account on this runner) are not.
  - **Levels and tiers:** `variants` are the reasoning levels routing admits for heads. `service_tiers` holds the tiers an account's plan includes and the runner can apply for that model's wire, and always includes `standard`.
  - **Side effects:** the query reserves, leases and records nothing.
  - **Callers:** Callosum's phone operator profile, the desktop operator route and `reserved:occipital`.
  - **Refusals:** `unknown_runner` for a runner routing doesn't know, and `routing_not_ready` with `retry_after_ms` while the catalog is still loading. (`crates/striatum-module/src/head_choices.rs`)

Non-quota refusals allow one atomic probe after at most one hour; a listing change, operator lift or successful request on the serving identity heals the fence. Subscription billing refusals consistent with quota become quota holds: newer fresh reserve-aware headroom heals them immediately, and without a current fresh reading they admit one probe every fifteen minutes. Among the eligible credentials and accounts the request permits, healthy choices are preferred over refusal probes; quota utilization never establishes entitlement. ## Subscription economics (2026-10-28)

Each candidate is priced on the estimated list cost of one task on that model: the trimmed per-task mean of its own token usage (fresh input, cached read, cache write, output, reasoning) for the request's workload and IQ bucket, priced at the model's own list rates. A task is every run of one work item, keyed by the `task_ref` core sends on routing/v1 `select`; usage rows carry the task key from their decision, and a task is treated as closed 24 hours after its last recorded usage. A cell with too few tasks borrows its profile through the transfer chain (own cell, same-family tier, family, scaled family, fleet bucket, fleet workload), and the decision records which level served. If any candidate on the shortlist has no profile, the whole selection keeps the class-vector pricing used before profiles existed. Profiles refresh every 15 minutes off the selection path. Metered pricing, adequacy gates, prompt-cache preference and the overqualification fit guard remain unchanged; overqualification now scales cost as described above; relative 10% economic bands give prices in the same band one cost key so adequacy can break the tie. (`crates/striatum-core/src/task_profile.rs`; `crates/striatum-core/src/model_router.rs`, `compute_profile_objective`, `route_order_keys`)

A subscription route costs `task list cost / M × pressure`, where M is the plan's quota multiplier (list USD per subscription USD of quota consumed). M is resolved **per subscription plan**: the plan's row in Astrocyte's `spend.multiplier.report` when that row is `routing_eligible` and its interval end is under the freshness limit, else the provider's operator `subscription_multiplier`, else **1** (labeled `default`, never a fabricated measurement). An account's plan is the `plan` of the report row whose `plan_prices` lists that account id; it is never rebuilt from provider and tier, because Antigravity readings say `antigravity` where the plan says `google/ultra_5x`. An account no row lists, or two rows list, has no measured plan. A provider whose accounts span several plans is priced at the harmonic mean of the plans' M weighted by each plan's spendable remaining points, the expected cost if usage spreads with capacity. Per-route operator multipliers and the legacy plan-fee-per-point conversion are gone: a per-route value loads with a warning naming it and is ignored. Decisions record each plan's M, source (`measured`, `operator`, `default`) and weight. (`crates/striatum-core/src/subscription.rs`, `SubscriptionPool::price`; `crates/striatum-module/src/subscription_economics.rs`, `measured`, `build`)

Subscription pricing multiplies the task's cost by a quota-scarcity factor called pressure. Its formula is parameter-free: `remaining window fraction / remaining headroom share²`, bounded to `[0.01, 1,000,000]`. It rises monotonically as headroom shrinks, steeply near a wall, and makes expiring unused headroom cheap. Weekly headroom is pooled across unwalled accounts, using `rawUsedPercent` when present; zeroed effective use from saved resets is not free live quota. Paid capacity remains 100 points per known account even when an account walls, so hitting a wall cannot reduce pressure by shrinking its denominator. The largest remaining weekly fraction in a pool governs time pressure; reported shorter windows are pooled by duration and the strongest window pressure governs. (`crates/striatum-core/src/subscription.rs`, `SubscriptionPlan::budget`)

`model_routing.keep_free_percent` is a provider-keyed map beside `subscription_multipliers`, validated in `0..100`, default 0. It is the only head-protection reservation: workers may spend the sum of `max(100 − raw use − margin, 0)` over live accounts whose weekly usage is below 100 and which have no short-window wall. Head callers named `alfonso`, `head`, `opencode`, `pi`, or `claude-code` ignore the margin, but not quota walls. Unknown caller classes are workers. If no eligible account has quota above its per-account keep-free margin, the route rejects workers as `subscription_reserve` (subject to the unchanged emergency banked-reset allowance below). Missing readings fail closed for workers with a nonzero margin. Setting the margin to zero removes head protection; neither recent head activity nor projected future demand can withhold live worker quota. Routing does not request `spend.multiplier.pace` or emit head-pace/reset-projection diagnostics. Astrocyte's `spend.multiplier.report` still supplies quota value for pricing; its fixture was captured from the real read-only operation and pins its source commit. (`crates/striatum-core/src/subscription.rs`, `SubscriptionPlan::budget`; `crates/striatum-module/src/subscription_economics.rs`, `refresh`)

`providers.<id>.banked_resets` accepts `"emergency"` (the default) or `"capacity"`. Emergency preserves the existing arithmetic: at no more than 10% live headroom, an account at at least 90% raw weekly use may lower pressure with one unexpired saved reset, earliest expiry first. Free unreserved live headroom on a different tier or provider plan disables that emergency credit. A banked reset contributes 100 points minus the provider's configured `keep_free_percent` for workers; it cannot reopen a 100% worker margin. Capacity instead counts every unexpired saved reset as an extra full weekly window in pressure: each adds 100 points to total capacity and 100 minus the worker margin to remaining headroom, even on an account at its weekly limit. Other plans do not disable capacity credit. Short-window pressure still governs when stronger. Insula's `credits[].expiresAt` removes each window at its expiry; counts without individual expiries use `soonestExpiresAt` when known. The setting changes pricing only, not plan multiplier weights, live available points, account admission, or reset application: an account at 100% cannot serve until the owner applies its reset. (`crates/striatum-core/src/subscription.rs`, `SubscriptionPlan::budget`, `capacity_pressure`; `crates/striatum-module/src/subscription_economics.rs`, `set_banked_allowance`)

The existing account-quota slow loop refreshes subscription value per point, plan prices, and pooled account headroom off the selection path (normally every 60 seconds). No selection performs a subc call. Account readings and roster metadata survive in routing's store; derived economics stay in memory, and non-stale readings older than 15 minutes lose authority, while a reading the producer marks as a stale last-good value stays usable up to 30 minutes from its producer timestamp. Missing Astrocyte/Fusiform modules and optional operations are normal, not routing errors. Decisions persist the pricing breakdown and explanation (task profile and transfer level, per-plan multiplier and source, pressure, fixed keep-free margin, banked use); route-dry-run already prints these explanation lines. Account-quota health lists each unknown/refused/overdue credential tier once as `unpriced plan tier: <provider>/<tier>`. (`crates/striatum-module/src/account_quota.rs`, `account_quota_loop`, `status_json`; `crates/striatum-module/src/subscription_economics.rs`, `health_detail`)

**Boundary:** the keep-free margin is enforced where the pooled plan budget is chosen, not inside `account_for`. The `account_for` allocator still chooses which account serves each model request and has no caller-class signal. Per-account fencing would require propagating that class into `account_for`; its runner field (Broca versus host plugin) is currently the closest proxy because heads do not run on Broca yet. Margin-based pricing therefore leaves the `account_for` API unchanged.

The scenario test with required IQ 70 (the caller's capability threshold on a 0–100 scale) uses Claude raw use 3%, 3%, 51%, 53% and one walled account, Codex Pro raw use 73% and 89% with saved resets, and a walled Pro Lite (`pro_100`, $100) plan. Both active plans cost $200. With 20% of each Claude weekly account window reserved from workers, Claude wins using $28.40/point versus Codex $9.42/point; raising Claude toward its reserved share flips the winner to Sol. Tests also pin source precedence, raw/effective use, margin/head distinction, zero-margin and nonzero-margin worker admission, pressure shape, expiring headroom, banked gating and unpriced-tier diagnostics. (`crates/striatum-core/tests/model_router.rs`; adapter and core subscription unit tests)

### Service-tier pricing

Routing retains Fusiform's `rate.<dimension>.mode.<tier>` facts alongside standard rates. For subscription traffic it scales the standard billing-plane basket before the existing output, basket or task-profile cost ladder runs: `included_usage_rate` while drawing included allowance, `credit_rate` only when a quota window is exhausted and purchased credits remain spendable. The current OpenAI plan facts state fast at 2.5× included usage / 2× credits and Pro 500 ultrafast at 8× / 6×. These are plan consumption rates, not API list-price ratios. API-key picks use only the requested mode's model rates; a missing mode dimension does not inherit its standard price. Missing prices remain unknown. Within a route, selection retains the least expensive eligible account draw (or the continuing account), and admission cannot replace it with a more expensive draw. (`account_selection.rs`, `ClassContext::apply_service_tier`; `service_tiers.rs`, `price_fact`)

## routing/v1: pins, preference, reports (cortexkit-role-routing 0.7.1)
The `routing/v1` surface (`crates/striatum-module/src/routing_v1/`) uses contract 0.7.1 and declares the optional groups `select_harness`, `select_hold_control`, `select_prefer`, `select_exclude_providers`, `select_task_ref`, `service_tier` and `account_continue` in `role.describe`. The older `route.select` (with `targetAgent`) and the older account ops (with `caller`) are unchanged.

- **Same-account holds.** When a conversation's account is blocked, routing advises waiting for it only if the blocking reset is a known future time and its Retry-After (rounded up, plus 0 to 20 seconds of jitter) fits within `min(hold_wait_max_s, max_hold_s)`. With several blocking windows the latest reset decides, and an unknown or unparseable reset moves the conversation. A cap of 0, `hold_ok: false` and the `Ordered` strategy never hold. Runners set the cap from their prompt cache, as `min(maxSameAccountWait, cacheExpiresAt - now)` in seconds, and send 0 when they have no record on that account, because waiting longer than the cache lives saves nothing. The provider ceiling `accounts.max_hold` defaults to 3600 seconds, and an omitted cap counts as 900. Selection saves the effective cap, and admission takes the smaller of its own cap, the saved cap and the current ceiling, so raising the ceiling never widens a decision already made. A reset beyond the ceiling records the blocking window as the reason for moving, and one within the ceiling but beyond the caller's cap records `HoldExceedsWait`. (`accounts/decide.rs`)

In `route.account_for` continue mode, a runner names its paused run, admission, previous decision and exhausted account evidence. Routing checks the stored run binding, records the evidence through the normal exhaustion path and reuses the account allocator within the previous provider, authentication method and model. The offered decision keeps the previous decision's selecting principal, consumer and project attribution rather than adopting a new owner scope. It never offers the exhausted account or an account under an applicable hold. Migration 072 stores each `selection_id` and its answer atomically with any offer reservation: identical retries replay it, and a changed question is `invalid_request` on `selection_id`. Offers link back to the previous decision and retain its pricing and task attribution; the first usage report consumes the reservation, otherwise expiry releases its demand. A hold names the earliest known candidate reset, omitting `until_ms` when unknown; caller-pinned accounts and disabled selection receive a final refusal.

Continue mode answers which other account can take the paused run, so the same-account hold rule above doesn't apply to it: the exhausted account is never offered, and a continue-mode `hold` reports when a replacement account frees up.

- **Service-tier selection.** An explicit `service_tier` is `standard`, `fast` or `ultrafast`. Non-standard candidates require the intersection of the model's mode-rate names, the vault credential's `plan_tier` joined to an established Fusiform `plan.prices.service_tiers` row, and the serving runner's levels for the route's `wire_api`. Unknown plans, absent or `not_established` inclusions, and missing runner declarations never establish eligibility. Standard is always tier-eligible. Routing runs the existing selection order and cost ladder at the requested tier, then retries lower levels only: ultrafast → fast → standard, never above the request. Answers and decision rows record `service_tier_chosen`, including fallback to standard. With no tier, the original selection path and omitted answer members are preserved. (`routing_v1/select.rs`, `select_with_profile_lookup`, `select_at_tier`)
- **Tier-aware runners and accounts.** The existing verified catalog declarations describe runner reach, but do not carry service-tier support. The same refresh now reads each declared runner's own `role.describe.service_tiers`, validated with llm-runner 0.7.36; failed reads remove tier support until the next successful refresh. Non-standard selections require a runner that follows routing's account choice. Each decision records its eligible credential set; both account admission surfaces enforce that set and recheck current plan, model and runner support. An account losing its entitlement cannot silently serve the old tier. (`routing_v1/runners.rs`, `refresh_loop`; `account_selection.rs`, `account_for`; store migration 071)
- **Tier affinity.** For the same principal, consumer and conversation affinity, a continuing decision keeps its tier and admitted credential while that credential can still serve it, even if a faster tier becomes available or another tier is cheaper. If the account cannot serve the tier, selection repeats the normal downward search. An explicit lower request remains a ceiling. An absent request retains legacy behavior. A changed tier rebuilds the runner's prompt cache, like a model change; routing therefore does not chase a cheaper tier mid-conversation. (`routing_v1/select.rs`, `select_with_profile_lookup`)
- **Tier reports.** Report usage accepts and preserves `service_tier_applied` and `service_tier_served`, including unfamiliar record strings. The usage-history row keeps both, its tier-priced cost and a price status. Served takes precedence over applied: a known served tier with complete token counts can be `confirmed`; an unfamiliar served tier or missing price/counts is `served_unpriced`, never priced at applied instead. Applied alone is `unconfirmed_estimate`. A missing count stays unknown and prevents a complete cost estimate; no reported output still means no usage-history row. Subscription costs here are quota-proxy dollars, not an additional subscription charge. Older routing decoders must not receive either report member unless they declare `service_tier`. (`routing_v1/report.rs`, `record_usage`; `service_tiers.rs`, `usage_cost`; store migration 071)

- **Pin fallback.** A pin is still hard admission. With `pin_fallback: "route"` a pin that cannot be served (any pin refusal: unknown model, excluded, cooldown, account refusal of the pinned route) is skipped and the whole order runs again without the request's pin: project pin, continuing model, operator ladder, then automatic selection, with the request's exclusions and requirements unchanged. Every answer to a pinned request carries `pin_outcome`: `pinned` when the pin was served, `fell_back` when it was skipped. A `fell_back` answer always carries `detail.pin_reason` (the `pin_unavailable` reason, or the refusal code for other pin refusals), even when `detail` was not asked for. The fallback answer is the one selection for the work. (`routing_v1/select.rs`, `select`, `refused_pin_reason`)
- **Prefer.** `prefer` (at most 16 `provider/model` keys, validated by the contract crate) ranks only within automatic selection: a request pin, the continuing (affinity) model and an operator ladder each decide first. The first listed route, in list order, that alone would be an adequate answer to the same request is answered: it must be among the routes the request may use (runners, requirements, exclusions, operator `not_for`, account preflight), clear the adequacy floor, and not queue on a full concurrency slot unless the normal answer queues too. Otherwise the normal answer stands. Demand is relative to the strongest routable fact (`striatum-core/src/route_scoring.rs`), so `iq: 100` is met by the best routable model; the conformance kit (0.7.1 and later) proves the no-inadequate-route rule on context window, not on iq. (`routing_v1/select.rs`, `Selection::preferred`)
- **Report quota fences.** A typed quota refusal (`account_limit_exhausted` or `quota_exhausted`) records the decision's route on the account that served it, even without a reset. A failed report carrying a future `reset_at_ms` also retains the legacy reset-evidence path. Only the decision's admitted identity, or a listed serving `credential_id` when no identity was bound, can receive that fence. Fresh reserve-aware headroom contradicting a quota refusal classifies it as non-quota, with a retry capped at one hour; otherwise quota evidence has no fixed expiry and newer fresh headroom lifts it immediately. Without a current fresh reading one atomic probe is permitted every fifteen minutes, and a reset adds a check without expiring evidence or extending that interval. A past date alone on an ordinary interruption is not a new quota refusal. The v1 and legacy `route.account_for` interfaces and select-side preflight respect the same scoped evidence, leaving healthy siblings available. When every offered account is fenced, `account_pool_exhausted` carries `reset_at_ms` for the earliest next check, not a promise that the fence ends then. Internal evidence and retry clocks are separate (migrations 067 and 082). (`routing_v1/report.rs`, `prepare_account_facts`; `account_selection.rs`, `roster_and_fences_for`, `route_fence_refusal`; `striatum-store/src/fence_rechecks.rs`)
- **Report usage.** `usage` carries `input_tokens` (no cache reads or writes), `cached_input_tokens`, `cache_write_tokens`, `output_tokens` (including `reasoning_tokens`), `reasoning_tokens`, `duration_ms`, `first_token_ms` and `cost_usd`; it is part of the report body for idempotency. The token counts join the route's usage history (`model_route_usage`, row id `routing-v1-report:<decision_id>`, workload class from the consumer) the same way `route.record_usage` rows do; a count the report leaves out is stored as unknown (NULL), never zero. The history cannot hold an unknown output count, so a report without `output_tokens` adds no history row. `duration_ms` is the run's wall clock, mostly tool time on an agentic run, so the row is written with the usage facts' `untimed` flag: it records no duration and is never a speed sample. Both timing members are kept only in the stored report body. (`routing_v1/report.rs`, `record_usage`; `striatum-core/src/model_resolution.rs`, `NativeUsageFacts::untimed`)
- **Run end.** `route.account_observe {kind: run_finished}` naming the admission marks it finished and ends the account pin's lease at once (`lease_valid_until` = now); `lease_valid_until_ms` is only the backstop. The admission's demand keeps counting until a quota reading reflects it. (`account_selection.rs`, `apply_bound_observation`)
