## Purpose
The routing plane joins catalog facts, operator policy, request demand, live quota, failure backoff, effective cost, and observed speed to select a reproducible provider/model route. It records every decision so later explanation can show the selected route, rejected candidates, provenance, objective, and outcome. (`crates/prefrontal-routing-core/src/model_router.rs:409-538`, `crates/prefrontal-routing-core/src/model_router.rs:557-631`, `crates/prefrontal-routing-module/src/main.rs:1918-1920`)

## Vocabulary
Route key: the canonical provider and model identity; Fusiform and the store key facts by provider plus model and never by a bare model id. (`crates/prefrontal-routing-store/tests/it/route_state_store.rs:2344-2383`)

Catalog fact: existence, token limits, capabilities, and output price synchronized from Fusiform, subject to a same-field operator override. (`crates/prefrontal-routing-module/src/fusiform_catalog.rs:3-12`, `crates/prefrontal-routing-core/src/route_state_store.rs:32-39`)

Score provenance: `Curated`, `Override`, `AaInferred`, or `Unscored`; unscored facts are known but not routable. (`crates/prefrontal-routing-core/src/model_facts.rs:178-204`)

Demand: IQ and EQ numbers must be within 0 through 100; the demand-bar calculation clamps its input to that same scale. (`crates/prefrontal-routing-core/src/routing_config.rs:48-62`, `crates/prefrontal-routing-core/src/model_router.rs:655-667`)

Demand bar: `top_score * (demand / 100)^0.35`; a model's fit on each demanded axis is capped at 1.0. (`crates/prefrontal-routing-core/src/routing_config.rs:13-13`, `crates/prefrontal-routing-core/src/routing_config.rs:48-62`)

Adequacy: the demand-weighted Elo and EQ fit after confidence penalty. Normal routing requires 0.90; best effort may run from 0.60 to 0.90 and emits `belowFloor`. (`crates/prefrontal-routing-core/src/route_scoring.rs:58-117`, `crates/prefrontal-routing-core/src/routing_config.rs:71-79`, `crates/prefrontal-routing-core/src/model_router.rs:727-776`)

Static admission: catalog, exclusion, availability, capability, context, and fast-variant gates applied before transient quota and cooldown state. (`crates/prefrontal-routing-core/src/model_router.rs:409-538`)

IQ frontier: the maximum Elo and EQ that an IQ request is measured against come from every route that could be chosen automatically, whether or not it can send right now. A route whose accounts are held by the reserve or exhausted, whose credential is refused or fenced, or whose credential listing is stale keeps its place in the frontier, so a walled top model never makes a weaker model count as adequate for higher IQ; the request waits or is refused instead. Routes with no serving credential, an incompatible runner pair, a capability mismatch, or an operator or caller exclusion (including pin-only models) stay out of the frontier. (`crates/prefrontal-routing-core/src/model_router.rs`, `admit_routes_with_availability`; `crates/prefrontal-routing-module/src/routing_v1/select.rs`)

Operator exclusion: `model_routing.exclude` (groups `all`, `mason`, `sidekick`, `athena`, `lab`, `core`, with `-` exceptions inside a group) keeps a route out of automatic choice only: unpinned `route.select`, class-policy panel seats and extra draws, fallback, failover, and reroute. A request that names its model (`work(model=...)`, a synthesizer or lab-planner pin, an admission pin) is admitted even when the route or its provider is excluded, as long as it is otherwise servable: credentials, availability, capability, context window, and quota walls still refuse it. There is no separate explicit-only list; `model_routing.explicit_only_providers` is refused at load with `config_key_removed` and the remedy "list the provider in model_routing.exclude.all; an explicit model pin is still admitted". (`crates/prefrontal-routing-module/src/work_model_pin.rs`, `crates/prefrontal-routing-module/src/select_policy.rs`, `crates/prefrontal-routing-module/src/config_overrides.rs`)

Variant overrides: `model_routing.variants` uses the same groups as `exclude` (`all`, `mason`, `sidekick`, `athena`, `lab`, `core`). Each group maps a route spec in the exclusion grammar (`provider`, `provider/model`, `provider/model/variant`; no `-` entries) to a reasoning variant, and within a group the most specific matching key wins. A selection runs at the first of: (1) a variant the caller names (`provider/model:variant`, an admission pin's or synthesizer pin's `variant`); (2) `variants.<consumer>`; (3) `variants.all`; (4) the curated default on the route's fact row. Panels apply it per seat, extra draws included: lab panels read `variants.lab`, every other class `variants.athena`. The authority for which variants exist is the catalog: Fusiform's `capability.reasoning_options`, whose `effort` values routing stores per model (`model_facts.reasoning_efforts_json`, migration 50). Startup (once the store opens) and every reload refuse an override whose variant a matched model does not publish, whose model publishes no effort values, or whose key matches no catalog model, naming the route, the variant and the published list; a refused reload keeps the last good config. `--check-config` runs the same check against the store at `$XDG_DATA_HOME/cortexkit/prefrontal-routing/store.db` (default `~/.local/share/...`) opened read-only, or prints why it skipped. A model not yet read from the catalog since migration 50 is a warning, not a refusal. If the catalog later stops publishing a configured variant, selection does not fail: it uses the next rule and records the skip in `variantSelection.fallbacks` on the `route.select` reply and as `variant fallback:` lines in the decision explanation. `route.select` replies carry `variantSelection` (`variant`, `source` = `pin`, `consumer`, `all` or `curated`); panel policies carry `reasoningVariant`, `reasoningVariantSource` and `reasoningVariantFallbacks` on each `seatedVariants` entry. (`crates/prefrontal-routing-module/src/variant_policy.rs`, `crates/prefrontal-routing-module/src/config_overrides.rs`, `crates/prefrontal-routing-store/src/reasoning_catalog.rs`, `crates/prefrontal-routing-module/src/fusiform_catalog.rs`)

Pinned variants: a `modelPin` naming `provider/model:variant` is checked against the same published efforts, following a `score_alias` provider to the provider whose catalog rows it borrows. A variant outside a published list is refused with `invalid_model_variant`, naming the list. A model the catalog has not been read for yet (or a module whose store has not opened) admits the pin, leaves the decision to Broca, and adds a `not checked` line to the decision explanation. Core runs each Athena seat (round zero, spec campaigns and replacement seats) at `seatedVariants[slot].reasoningVariant` when routing sends it, and at the member's `promptParams.variant` otherwise. It records the result as `seatVariant {variant, source}` on the member in the consult's stored panel; the source is routing's `reasoningVariantSource`, or `prompt_params` when routing sent no per-seat variant. (`crates/prefrontal-routing-module/src/work_model_pin.rs`, `crates/prefrontal-core-module/src/routing_cooldown.rs`)

Effective price: output list price divided by a positive finite subscription multiplier; unknown price normalizes to maximum cost rather than zero. An explicit service tier scales subscription consumption by the account plan's included-usage or credit rate; API-key traffic uses the model's mode rates instead. (`crates/prefrontal-routing-core/src/model_router.rs`; `crates/prefrontal-routing-module/src/service_tiers.rs`)

Selection cost: normalized effective price plus quota pressure weighted by 0.5. (`crates/prefrontal-routing-core/src/model_router.rs:557-631`, `crates/prefrontal-routing-core/src/routing_config.rs:84-86`)

Effectively-free bucket: routes at or below selection cost 0.05 compare adequacy before speed and ignore smaller cost differences. (`crates/prefrontal-routing-core/src/routing_config.rs:82-82`, `crates/prefrontal-routing-core/src/model_router.rs:831-848`)

Quota wall: a route or account exclusion caused by explicit exhaustion, utilization at or above 0.99, or a reported spendable non-positive pool. (`crates/prefrontal-routing-core/src/quota.rs:249-306`, `crates/prefrontal-routing-core/src/quota.rs:114-125`)

Failure backoff: route-local cooldown whose default threshold is three consecutive route-attributable terminal failures; it begins at ten minutes and doubles to a six-hour cap. (`crates/prefrontal-routing-core/src/failure_backoff.rs:8-23`, `crates/prefrontal-routing-core/src/failure_backoff.rs:132-182`)

Routing decision: the durable selected route, request, candidate explanations, policy provenance, and later outcome addressed by decision id or send id. (`crates/prefrontal-routing-store/src/lib.rs:485-537`, `crates/prefrontal-routing-module/src/main.rs:3166-3282`)

## Lifecycle
1. Fusiform synchronization decodes served catalog rates as priced, stated-zero, unpriced, or refused; non-USD, negative, and excessive-exponent prices become unknown maximum cost rather than crashing selection. (`crates/prefrontal-routing-module/src/fusiform_catalog.rs:126-219`)
2. First-sight models under operator-known providers enter the store as unscored and cannot route until an operator override, curated seed, or AA inference supplies score placement. (`crates/prefrontal-routing-store/src/lib.rs:830-845`, `crates/prefrontal-routing-core/src/model_facts.rs:202-204`)
3. AA maps an exact route key to an index, interpolates the embedded Elo curve, applies a 30 percent floor-gap penalty, inherits EQ from the closest curated neighbor, and uses default speed 100. (`crates/prefrontal-routing-core/src/aa_infer.rs:21-54`, `crates/prefrontal-routing-core/src/aa_infer.rs:103-169`)
4. Policy resolution combines curated and authenticated subscription providers, operator rules, and caller rules. Operator factual overrides remain authoritative, and operator exclusions are authoritative for automatic choice; a request that names its model keeps excluded routes in its available set. (`crates/prefrontal-routing-core/src/launch_policy.rs:140-196`, `crates/prefrontal-routing-core/src/provider_model_spec.rs:137-176`)
5. Selection validates IQ and EQ, rejects statically inadmissible routes, overlays cooldown, quota, and failure backoff, and computes the top routable quality frontier without transient walls, account availability, credential refusals or stale credential listings (see IQ frontier above). (`crates/prefrontal-routing-core/src/model_router.rs:409-538`, `crates/prefrontal-routing-core/src/model_router.rs:655-683`)
6. The scorer refuses below 0.60, uses best effort from 0.60 through 0.90, and normally shortlists only routes at or above 0.90. Cheapness and speed cannot pull a sub-bar model into the shortlist. (`crates/prefrontal-routing-core/src/model_router.rs:727-776`, `crates/prefrontal-routing-core/tests/model_router.rs:207-210`)
7. Within the shortlist, the scorer compares prompt-cache preference and selection cost; two effectively-free routes compare adequacy, then normalized speed from 50 to 200 tokens per second. (`crates/prefrontal-routing-core/src/model_router.rs:831-848`, `crates/prefrontal-routing-core/src/model_router.rs:541-543`)
8. Quota merging walls a route at explicit exhaustion or 99 percent use. Missing reset time uses a six-hour reprobe horizon; if every candidate is exhausted, break-glass probes the earliest reset across route and capacity scopes. (`crates/prefrontal-routing-core/src/quota.rs:249-306`, `crates/prefrontal-routing-core/src/break_glass.rs:72-130`)
9. Panel selection shares route admission and seats at most one model per served lineage, counting missing lineage as the single `other` family. It reports a diversity shortfall when too few distinct families remain. Seat selection evaluates a model pin first and then recommendation tiers. (`crates/prefrontal-routing-core/src/panel.rs`, `crates/prefrontal-routing-core/src/seat_routing.rs`)
10. The module records the chosen decision and every rejected candidate before returning; later outcome reports update the record and failure streak. (`crates/prefrontal-routing-module/src/main.rs:2684-2772`, `crates/prefrontal-routing-store/src/lib.rs:1704-1749`, `crates/prefrontal-routing-module/src/main.rs:2924-2992`)
11. Usage reports add observed speed samples. Five qualifying recent samples replace the static speed input on later selections. (`crates/prefrontal-routing-store/src/lib.rs:2008-2020`, `crates/prefrontal-routing-store/src/lib.rs:2099-2136`)
12. On restart, the store migrations and open path restore durable facts, cursors, backoff, usage, and decisions; background Fusiform, AA, and quota consumers refresh external state. (`crates/prefrontal-routing-store/src/lib.rs:143-282`, `crates/prefrontal-routing-store/src/lib.rs:558-579`, `crates/prefrontal-routing-module/src/main.rs:113-123`)

## Subscription economics (2026-10-28)

Each candidate is priced on the estimated list cost of one task on that model: the trimmed per-task mean of its own token usage (fresh input, cached read, cache write, output, reasoning) for the request's workload and IQ bucket, priced at the model's own list rates. A task is every run of one work item, keyed by the `task_ref` core sends on routing/v1 `select`; usage rows carry the task key from their decision, and a task is treated as closed 24 hours after its last recorded usage. A cell with too few tasks borrows its profile through the transfer chain (own cell, same-family tier, family, scaled family, fleet bucket, fleet workload), and the decision records which level served. If any candidate on the shortlist has no profile, the whole selection keeps the class-vector pricing used before profiles existed. Profiles refresh every 15 minutes off the selection path. Metered pricing, adequacy gates, prompt-cache preference, overqualification and its fit guard remain unchanged; relative 10% economic bands give prices in the same band one cost key so adequacy can break the tie. (`crates/prefrontal-routing-core/src/task_profile.rs`; `crates/prefrontal-routing-core/src/model_router.rs`, `compute_profile_objective`, `route_order_keys`)

A subscription route costs `task list cost / M × pressure`, where M is the plan's quota multiplier (list USD per subscription USD of quota consumed). M is resolved **per subscription plan**: the plan's row in Astrocyte's `spend.multiplier.report` when that row is `routing_eligible` and its interval end is under the freshness limit, else the provider's operator `subscription_multiplier`, else **1** (labeled `default`, never a fabricated measurement). An account's plan is the `plan` of the report row whose `plan_prices` lists that account id; it is never rebuilt from provider and tier, because Antigravity readings say `antigravity` where the plan says `google/ultra_5x`. An account no row lists, or two rows list, has no measured plan. A provider whose accounts span several plans is priced at the harmonic mean of the plans' M weighted by each plan's spendable remaining points, the expected cost if usage spreads with capacity. Per-route operator multipliers and the legacy plan-fee-per-point conversion are gone: a per-route value loads with a warning naming it and is ignored. Decisions record each plan's M, source (`measured`, `operator`, `default`) and weight. (`crates/prefrontal-routing-core/src/subscription.rs`, `SubscriptionPool::price`; `crates/prefrontal-routing-module/src/subscription_economics.rs`, `measured`, `build`)

Subscription pricing multiplies the task's cost by a quota-scarcity factor called pressure. Its formula is parameter-free: `remaining window fraction / remaining headroom share²`, bounded to `[0.01, 1,000,000]`. It rises monotonically as headroom shrinks, steeply near a wall, and makes expiring unused headroom cheap. Weekly headroom is pooled across unwalled accounts, using `rawUsedPercent` when present; zeroed effective use from saved resets is not free live quota. Paid capacity remains 100 points per known account even when an account walls, so hitting a wall cannot reduce pressure by shrinking its denominator. The largest remaining weekly fraction in a pool governs time pressure; reported shorter windows are pooled by duration and the strongest window pressure governs. (`crates/prefrontal-routing-core/src/subscription.rs`, `SubscriptionPlan::budget`)

`model_routing.keep_free_percent` is a provider-keyed map beside `subscription_multipliers`, validated in `0..100`, default 0. It is the only head-protection reservation: workers may spend the sum of `max(100 − raw use − margin, 0)` over live accounts whose weekly usage is below 100 and which have no short-window wall. Head callers named `alfonso`, `head`, `opencode`, `pi`, or `claude-code` ignore the margin, but not quota walls. Unknown caller classes are workers. If no eligible account has quota above its per-account keep-free margin, the route rejects workers as `subscription_reserve` (subject to the unchanged emergency banked-reset allowance below). Missing readings fail closed for workers with a nonzero margin. Setting the margin to zero removes head protection; neither recent head activity nor projected future demand can withhold live worker quota. Routing does not request `spend.multiplier.pace` or emit head-pace/reset-projection diagnostics. Astrocyte's `spend.multiplier.report` still supplies quota value for pricing; its fixture was captured from the real read-only operation and pins its source commit. (`crates/prefrontal-routing-core/src/subscription.rs`, `SubscriptionPlan::budget`; `crates/prefrontal-routing-module/src/subscription_economics.rs`, `refresh`)

Banked resets are outside live headroom. At no more than 10% live headroom, an account at at least 90% raw weekly use may lower pressure with one unexpired saved reset, earliest expiry first. Free unreserved live headroom on a different tier or provider plan disables that emergency credit. A banked reset contributes 100 points minus the provider's configured `keep_free_percent` for workers; it cannot reopen a 100% worker margin. Insula's `soonestExpiresAt` and `credits[].expiresAt` determine expiry. (`crates/prefrontal-routing-core/src/subscription.rs`, `SubscriptionPlan::budget`; `crates/prefrontal-routing-module/src/subscription_economics.rs`, `set_banked_allowance`)

The existing account-quota slow loop refreshes subscription value per point, plan prices, and pooled account headroom off the selection path (normally every 60 seconds). No selection performs a subc call. Account readings and roster metadata survive in routing's store; derived economics stay in memory, and non-stale readings older than 15 minutes lose authority, while a reading the producer marks as a stale last-good value stays usable up to 30 minutes from its producer timestamp. Missing Astrocyte/Fusiform modules and optional operations are normal, not routing errors. Decisions persist the pricing breakdown and explanation (task profile and transfer level, per-plan multiplier and source, pressure, fixed keep-free margin, banked use); route-dry-run already prints these explanation lines. Account-quota health lists each unknown/refused/overdue credential tier once as `unpriced plan tier: <provider>/<tier>`. (`crates/prefrontal-routing-module/src/account_quota.rs`, `account_quota_loop`, `status_json`; `crates/prefrontal-routing-module/src/subscription_economics.rs`, `health_detail`)

**Boundary:** the keep-free margin is enforced where the pooled plan budget is chosen, not inside `account_for`. The `account_for` allocator still chooses which account serves each model request and has no caller-class signal. Per-account fencing would require propagating that class into `account_for`; its runner field (Broca versus host plugin) is currently the closest proxy because heads do not run on Broca yet. Margin-based pricing therefore leaves the `account_for` API unchanged.

The scenario test with required IQ 70 (the caller's capability threshold on a 0–100 scale) uses Claude raw use 3%, 3%, 51%, 53% and one walled account, Codex Pro raw use 73% and 89% with saved resets, and a walled Pro Lite (`pro_100`, $100) plan. Both active plans cost $200. With 20% of each Claude weekly account window reserved from workers, Claude wins using $28.40/point versus Codex $9.42/point; raising Claude toward its reserved share flips the winner to Sol. Tests also pin source precedence, raw/effective use, margin/head distinction, zero-margin and nonzero-margin worker admission, pressure shape, expiring headroom, banked gating and unpriced-tier diagnostics. (`crates/prefrontal-routing-core/tests/model_router.rs`; adapter and core subscription unit tests)

### Service-tier pricing

Routing retains Fusiform's `rate.<dimension>.mode.<tier>` facts alongside standard rates. For subscription traffic it scales the standard billing-plane basket before the existing output, basket or task-profile cost ladder runs: `included_usage_rate` while drawing included allowance, `credit_rate` only when a quota window is exhausted and purchased credits remain spendable. The current OpenAI plan facts state fast at 2.5× included usage / 2× credits and Pro 500 ultrafast at 8× / 6×. These are plan consumption rates, not API list-price ratios. API-key picks use only the requested mode's model rates; a missing mode dimension does not inherit its standard price. Missing prices remain unknown. Within a route, selection retains the least expensive eligible account draw (or the continuing account), and admission cannot replace it with a more expensive draw. (`account_selection.rs`, `ClassContext::apply_service_tier`; `service_tiers.rs`, `price_fact`)

## routing/v1: pins, preference, reports (cortexkit-role-routing 0.5.7)
The `routing/v1` surface (`crates/prefrontal-routing-module/src/routing_v1/`) serves contract 0.5.7 and declares the optional groups `select_harness`, `select_hold_control`, `select_prefer`, `select_exclude_providers`, `select_task_ref`, `service_tier` and `account_continue` in `role.describe`. The older `route.select` (with `targetAgent`) and the older account ops (with `caller`) are unchanged.

- **Same-account holds.** When a conversation's account is blocked, routing advises waiting for it only if the blocking reset is a known future time and its Retry-After (rounded up, plus 0 to 20 seconds of jitter) fits within `min(hold_wait_max_s, max_hold_s)`. With several blocking windows the latest reset decides, and an unknown or unparseable reset moves the conversation. A cap of 0, `hold_ok: false` and the `Ordered` strategy never hold. Runners set the cap from their prompt cache, as `min(maxSameAccountWait, cacheExpiresAt - now)` in seconds, and send 0 when they have no record on that account, because waiting longer than the cache lives saves nothing. The provider ceiling `accounts.max_hold` defaults to 3600 seconds, and an omitted cap counts as 900. Selection saves the effective cap, and admission takes the smaller of its own cap, the saved cap and the current ceiling, so raising the ceiling never widens a decision already made. A reset beyond the ceiling records the blocking window as the reason for moving, and one within the ceiling but beyond the caller's cap records `HoldExceedsWait`. (`accounts/decide.rs`)

In `route.account_for` continue mode, a runner names its paused run, admission, previous decision and exhausted account evidence. Routing checks the stored run binding, records the evidence through the normal exhaustion path and reuses the account allocator within the previous provider, authentication method and model. The offered decision keeps the previous decision's selecting principal, consumer and project attribution rather than adopting a new owner scope. It never offers the exhausted account or an account under an applicable hold. Migration 072 stores each `selection_id` and its answer atomically with any offer reservation: identical retries replay it, and a changed question is `invalid_request` on `selection_id`. Offers link back to the previous decision and retain its pricing and task attribution; the first usage report consumes the reservation, otherwise expiry releases its demand. A hold names the earliest known candidate reset, omitting `until_ms` when unknown; caller-pinned accounts and disabled selection receive a final refusal.

Continue mode answers which other account can take the paused run, so the same-account hold rule above doesn't apply to it: the exhausted account is never offered, and a continue-mode `hold` reports when a replacement account frees up.

- **Service-tier selection.** An explicit `service_tier` is `standard`, `fast` or `ultrafast`. Non-standard candidates require the intersection of the model's mode-rate names, the vault credential's `plan_tier` joined to an established Fusiform `plan.prices.service_tiers` row, and the serving runner's levels for the route's `wire_api`. Unknown plans, absent or `not_established` inclusions, and missing runner declarations never establish eligibility. Standard is always tier-eligible. Routing runs the existing selection order and cost ladder at the requested tier, then retries lower levels only: ultrafast → fast → standard, never above the request. Answers and decision rows record `service_tier_chosen`, including fallback to standard. With no tier, the original selection path and omitted answer members are preserved. (`routing_v1/select.rs`, `select_with_profile_lookup`, `select_at_tier`)
- **Tier-aware runners and accounts.** The existing verified catalog declarations describe runner reach, but do not carry service-tier support. The same refresh now reads each declared runner's own `role.describe.service_tiers`, validated with llm-runner 0.7.36; failed reads remove tier support until the next successful refresh. Non-standard selections require a runner that follows routing's account choice. Each decision records its eligible credential set; both account admission surfaces enforce that set and recheck current plan, model and runner support. An account losing its entitlement cannot silently serve the old tier. (`routing_v1/runners.rs`, `refresh_loop`; `account_selection.rs`, `account_for`; store migration 071)
- **Tier affinity.** For the same principal, consumer and conversation affinity, a continuing decision keeps its tier and admitted credential while that credential can still serve it, even if a faster tier becomes available or another tier is cheaper. If the account cannot serve the tier, selection repeats the normal downward search. An explicit lower request remains a ceiling. An absent request retains legacy behavior. A changed tier rebuilds the runner's prompt cache, like a model change; routing therefore does not chase a cheaper tier mid-conversation. (`routing_v1/select.rs`, `select_with_profile_lookup`)
- **Tier reports.** Report usage accepts and preserves `service_tier_applied` and `service_tier_served`, including unfamiliar record strings. The usage-history row keeps both, its tier-priced cost and a price status. Served takes precedence over applied: a known served tier with complete token counts can be `confirmed`; an unfamiliar served tier or missing price/counts is `served_unpriced`, never priced at applied instead. Applied alone is `unconfirmed_estimate`. A missing count stays unknown and prevents a complete cost estimate; no reported output still means no usage-history row. Subscription costs here are quota-proxy dollars, not an additional subscription charge. Older routing decoders must not receive either report member unless they declare `service_tier`. (`routing_v1/report.rs`, `record_usage`; `service_tiers.rs`, `usage_cost`; store migration 071)

- **Pin fallback.** A pin is still hard admission. With `pin_fallback: "route"` a pin that cannot be served (any pin refusal: unknown model, excluded, cooldown, account refusal of the pinned route) is skipped and the whole order runs again without the request's pin: project pin, continuing model, operator ladder, then automatic selection, with the request's exclusions and requirements unchanged. Every answer to a pinned request carries `pin_outcome`: `pinned` when the pin was served, `fell_back` when it was skipped. A `fell_back` answer always carries `detail.pin_reason` (the `pin_unavailable` reason, or the refusal code for other pin refusals), even when `detail` was not asked for. The fallback answer is the one selection for the work. (`routing_v1/select.rs`, `select`, `refused_pin_reason`)
- **Prefer.** `prefer` (at most 16 `provider/model` keys, validated by the contract crate) ranks only within automatic selection: a request pin, the continuing (affinity) model and an operator ladder each decide first. The first listed route, in list order, that alone would be an adequate answer to the same request is answered: it must be among the routes the request may use (runners, requirements, exclusions, operator `not_for`, account preflight), clear the adequacy floor, and not queue on a full concurrency slot unless the normal answer queues too. Otherwise the normal answer stands. Demand is relative to the strongest routable fact (`prefrontal-routing-core/src/route_scoring.rs`), so `iq: 100` is met by the best routable model; the conformance kit (0.7.1 and later) proves the no-inadequate-route rule on context window, not on iq. (`routing_v1/select.rs`, `Selection::preferred`)
- **Report reset fences.** A `route.report` with `outcome: failed` and a future `reset_at_ms` closes the decision's route (provider and model) on the account that served it until the reset, capped at 24 hours from the report. The serving account is the identity routing admitted for the decision, else the report's `credential_id`, and only a credential the vault lists for that route counts. A reset already past records the failure with no fence, and other outcomes never fence. Fences live in `account_route_fence` (migration 067, carried by every backup); two reports keep the later reset; ended rows are deleted when read. `route.account_for` (both surfaces) leaves fenced accounts out of the route's roster, so other accounts and other routes on the same account are untouched; when every account the request may use (its `candidates`, if sent) is fenced, it refuses `account_pool_exhausted` with `reset_at_ms` at the earliest fence end. Select-side account preflight sees the same roster. (`routing_v1/report.rs`, `record_account_facts`; `account_selection.rs`, `roster_and_fences_for`, `route_fence_refusal`; `prefrontal-routing-store/migrations/067_account_route_fence.sql`)
- **Report usage.** `usage` carries `input_tokens` (no cache reads or writes), `cached_input_tokens`, `cache_write_tokens`, `output_tokens` (including `reasoning_tokens`), `reasoning_tokens`, `duration_ms`, `first_token_ms` and `cost_usd`; it is part of the report body for idempotency. The token counts join the route's usage history (`model_route_usage`, row id `routing-v1-report:<decision_id>`, workload class from the consumer) the same way `route.record_usage` rows do; a count the report leaves out is stored as unknown (NULL), never zero. The history cannot hold an unknown output count, so a report without `output_tokens` adds no history row. `duration_ms` is the run's wall clock, mostly tool time on an agentic run, so the row is written with the usage facts' `untimed` flag: it records no duration and is never a speed sample. Both timing members are kept only in the stored report body. (`routing_v1/report.rs`, `record_usage`; `prefrontal-routing-core/src/model_resolution.rs`, `NativeUsageFacts::untimed`)
- **Run end.** `route.account_observe {kind: run_finished}` naming the admission marks it finished and ends the account pin's lease at once (`lease_valid_until` = now); `lease_valid_until_ms` is only the backstop. The admission's demand keeps counting until a quota reading reflects it. (`account_selection.rs`, `apply_bound_observation`)
