# Routing baseline recordings

These are observations of the pre-cutover implementation, not desired 0.7.1
answers. The recording build retains routing 0.6.0 / conformance 0.9.0. Tests
control time and generated identities only; production dispatch, admission,
selection and effect writers are unchanged.

## Inputs and provenance

- `core.requests.json` is generated by core's `LazyRoutingCooldownRecorder` and
  selection builders in `routing_replay_core_tests.rs`. Core tests compare its
  exact outbound bodies with this file; routing reads it by path. The test's
  transport answers are only a capture aid, not the routing oracle.
- `clients/` preserves the owner-supplied JSON bytes. `clients/SOURCES.md` names
  the encoders, owners and collection date. Each recorded body has a SHA-256 in
  `client-shapes.golden.json`. Setup calls are explicitly separate from the
  unchanged client body. They create the synthetic decisions/admissions the
  supplied IDs name; they are not claimed as captured client traffic.
- `client-sets.json` inventories each client shape, including explicit blocked
  sets and Basal's empty, no-calls-observed set. A blocked set is never filled by
  a conformance example or an invented body. CKDesk's source is built but not
  live; Thalamus's two principals share the supplied relay bodies.
- `report-outcomes.requests.json` contains **policy probes**, not client traffic.
  It includes each report outcome string and the provider/model/credential boundary
  blocked until a reported future reset time.
- `availability.golden.json` records cooldown-status alongside fallback,
  no-fallback and isolated-probe requests for each named cause. Each case begins
  with a live affinity; probe settlement and the standing affinity are recorded.
  The answers include today's held-account and saturated-capacity behavior;
  they must not be interpreted as the future contract's availability policy.
- `panels.golden.json` records named Athena AUDIT and Spec round-zero SPEC cases,
  their catalog and policy, complete replies and each seat's package ceiling.
  `budgets.golden.json` additionally records zero, placeholder, missing and
  exhausted-window facts separately. These are old formulas, not the desired contract 0.7.1 budget results.
- `tier-consumers.golden.json` records explicit designer/synthesizer lookup,
  slot-resolved lookup and consumer fallback against different settings tiers.
  Core's request fixture separately records its explicit-before-slot resolver.
- `usage.golden.json` records core's real Broca-run usage builder for each launch
  label, including visible versus reasoning tokens, workload and absent account.
  `model-facts.golden.json` records the old raw fact read, including zero and
  placeholder output limits. `available-models.golden.json` freezes both include
  settings with excluded, unscored subscription, fractional and deprecated rows.

Persistent snapshots include cooldown, health/penalty, decision scope, usage,
affinity, credential entitlement blocks, account/route reset blocks, admissions
and pool state. The credential blocks retain the credential, provider/model,
reason and reset time that stop a new admission. Untouched neutral rows
for the bundled catalog are omitted; every non-neutral field is retained.
Scratch directory names are replaced with `<replay>` / `<scratch>`. No reply
member, identity, timestamp or non-neutral effect is masked.

## Difference 10: routing's available-models text operation

Routing no longer advertises or handles `routing.available_models_text`; requests
now receive `unknown_method`. Core's operation with the same name is separate:
core renders the text from `route.consumer_models` and Fusiform and keeps serving
its existing callers. Rolling core back past that switch after routing's deletion
is unsupported.

The historical text request and golden remain intact. The core replay comparison
changes only that step's reply and frame type for difference 10, retaining its
state and all other steps. `available-models.golden.json` remains the pre-switch
rendering oracle for the consumer-model inventory and core's renderer.

No other method or legacy shape is removed. `route.cooldown_status` and
`route.model_fact`, like the legacy shapes, remain until both an empty caller
census and a fleet-wide fourteen-day zero-call window are established. The window
starts no earlier than the latest counter deployment, switched-core deployment
and last older-core exit; a local store's counts alone do not authorize deletion.

## Difference 14

`core.golden.json` / `difference-14-core-A-task-B` sends core's request with
`project_root: /replay/project-B` over a connection stamped `project-A`. The
operator config pins A to `example-provider/model-a` and B to `model-b`. Today's
answer and durable v1 decision name A's model and `project-A`.

The following **legacy token relay** row names A's selected model but has no
project/task/account attribution: its `task_id`, `task_workload`, and
`account_key` are null, and that table has no project column. This is an observed
limitation, not a claim that today's relay attributes a project profile to A.
The post-cutover core must attribute operator pins, cost and per-task token
profiles to project B. It must not rewrite this baseline as though the old
relay already carried those project-attribution fields.

## Explain spelling evidence

Core's captured read sends `decisionID`. None of the supplied Broca, Thalamus,
Magic Context, Occipital or CKDesk body files sends `route.explain`. The owner
source notes explicitly say Occipital only calls `route.catalog_targets`, and
CKDesk only has the not-yet-live head-choices read. Frozen conformance examples
send `{decision_id}`, but a conformance check is not evidence that a fleet
client sends it. The corpus-wide answer remains incomplete while a named
client set is blocked; consult `recording-status.json`, not an inferred “none”.

## Re-recording

### Public availability replies

`availability-public.golden.json` contains the public `routing/v1` select
requests and real-handler reply bodies for all 13 availability scenarios,
with fallback, no-fallback and zero-wait probe launches for each scenario.
The clock and generated IDs are controlled by the same recorder as the
historical availability fixture; no reply is assembled by the test.

`availability.golden.json` remains the historical recording.
`availability-difference.json` declares exact before/after changes by row:

- `credential-fence`: a failed report has blocked the route on every account;
  public pin refusals retain the time when the first account's block expires.
- `no-eligible-account`: the zero-wait probe retains the known quota reset.
- `all-accounts-held`: the zero-wait probe retains the short quota reset;
  selections whose wait limit permits the runner to wait for an account still
  answer normally, with the wait happening later at `route.account_for`.
- `unknown-reset`: the public pin refusal remains untimed.

Those differences also record the newly persisted pin refusals and the
account-limit reason on fallback answers. Other historical observations are
still compared unchanged. As in the other replay tests, comparison omits
newer delivery-identity tables and stored selection snapshots, which have
dedicated persistence tests and are absent from the historical recording.

To re-record only the public export, run:

```sh
PREFRONTAL_RECORD_ROUTING_PUBLIC_AVAILABILITY=1 cargo nextest run --locked -p prefrontal-routing-module --bin ck-striatum -E 'test(=routing_v1::replay_tests::replay_availability_cases)'
```

For remote recording, return
`crates/prefrontal-routing-module/fixtures/replay/availability-public.golden.json`.
Without that variable the same test compares both the public export and the
historical recording with its declared differences.

### Historical recordings

Set `PREFRONTAL_RECORD_ROUTING_REPLAY=1` only for intentional baseline generation.
Run core's two `replay_core_*` / `core_replay_requests_match_recording` tests
first, then routing's `replay_*` tests. A remote generation job must list each
changed fixture in `return_paths`. Tests without the variable compare against
the checked-in data and never update it. Keep return batches under 10 MiB.
Follow `.cortexkit/WORKER.md` at the repository root. For example:

```sh
cargo nextest run --locked -p prefrontal-core-module --lib --bins -E 'test(=routing_cooldown::v1_select_wire_tests::core_replay_requests_match_recording) | test(/replay_core_usage_attribution$/)'
cargo nextest run --locked -p prefrontal-routing-module --bin ck-striatum -E 'test(/^routing_v1::replay_tests::/)'
```

The panel, tier-consumer, model-fact and renderer recorders also have `replay_`
in their test names, under their own modules. Filter those names explicitly;
do not run a whole package.
